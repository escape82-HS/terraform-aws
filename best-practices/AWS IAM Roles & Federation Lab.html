AWS IAM Federation Lab

Gestione Identità, Ruoli e Integrazione SAML 2.0

1. IAM Users vs. IAM Roles

La distinzione fondamentale in AWS Security è tra identità permanenti e temporanee.

Caratteristica IAM User (Utente) IAM Role (Ruolo)
Natura Identità permanente associata a una persona o servizio specifico. Identità temporanea che può essere "assunta" da chiunque ne abbia il permesso.
Credenziali Password (Console) o Access Keys (CLI) a lungo termine. Token di sicurezza temporanei (STS) che scadono (da 15 min a 12 ore).
Best Practice Usare SOLO per creare l'account iniziale o per casi legacy molto specifici. Standard moderno. Usato per EC2, Lambda, Cross-Account e Federation.
Rischio Alto. Se le chiavi vengono rubate, l'hacker ha accesso finché non vengono revocate. Basso. Se il token viene rubato, scade automaticamente dopo poco tempo.

2. Teoria: SAML Federation Flow

Come fa un utente che si logga sul computer aziendale (Active Directory/Okta) ad accedere alla console AWS senza creare un utente IAM?

1. User Login
Utente accede al portale IdP (es. Okta)
→
2. SAML Assertion
IdP genera un file XML firmato che dice "Questo è Mario Rossi"
→
3. AWS Sign-in
Browser invia l'XML all'endpoint AWS SAML
→
4. STS AssumeRole
AWS valida la firma e scambia l'XML con Token Temporanei
→
5. Accesso
Utente entra in Console con i permessi del Ruolo
Vantaggio Chiave: Le credenziali non sono mai salvate in AWS. La gestione (assunzioni, licenziamenti, reset password) avviene solo nell'IdP aziendale.

3. Lab: Configurazione Lato AWS

In questo lab configureremo la parte AWS per fidarsi di un provider esterno. Poiché non abbiamo un vero server Active Directory, simuleremo il file di metadati.

1Creazione File Metadata XML (Simulato)

Crea un file sul tuo desktop chiamato saml-metadata.xml e incolla questo contenuto (è un placeholder valido per AWS):

<EntityDescriptor entityID="http://www.okta.com/exk12345" xmlns="urn:oasis:names:tc:SAML:2.0:metadata">
  <IDPSSODescriptor protocolSupportEnumeration="urn:oasis:names:tc:SAML:2.0:protocol">
    <KeyDescriptor use="signing">
      <ds:KeyInfo xmlns:ds="http://www.w3.org/2000/09/xmldsig#">
        <ds:X509Data>
          <ds:X509Certificate>MIIDpDCCAoygAwIBAgIGAV2... (TRUNCATED FOR LAB) ...</ds:X509Certificate>
        </ds:X509Data>
      </ds:KeyInfo>
    </KeyDescriptor>
    <SingleSignOnService Binding="urn:oasis:names:tc:SAML:2.0:bindings:HTTP-POST" Location="https://dev-123456.oktapreview.com/app/exk12345/sso/saml"/>
  </IDPSSODescriptor>
</EntityDescriptor>
Nota: Questo XML serve solo a sbloccare l'interfaccia AWS. Non funzionerà per un login reale senza un vero IdP.

2Creazione Identity Provider (IdP)

  1. Vai alla console IAM.
  2. Nel menu a sinistra, clicca su Identity providers.
  3. Clicca Add provider.
  4. Provider type: SAML.
  5. Provider name: MyCorporateIdP.
  6. Metadata document: Carica il file saml-metadata.xml creato prima.
  7. Clicca Add provider.

Ora AWS "conosce" e si fida dell'entità descritta in quel file.

4. Creazione del Ruolo Federato

Ora creiamo il ruolo che gli utenti dell'IdP assumeranno.

3Configurazione Trust Relationship

  1. Vai su Roles -> Create role.
  2. Trusted entity type: SAML 2.0 federation.
  3. Choose a SAML 2.0 provider: Seleziona MyCorporateIdP.
  4. Allow programmatic and AWS Management Console access: Seleziona questa opzione.
  5. Clicca Next.

4Permessi e Finalizzazione

  1. Add permissions: Cerca e seleziona ViewOnlyAccess (Per sicurezza, diamo solo permessi di lettura).
  2. Clicca Next.
  3. Role name: SAML-ViewOnly-Role.
  4. Clicca Create role.

5Analisi della Trust Policy

Vai nel ruolo appena creato e clicca sul tab Trust relationships. Vedrai un JSON simile a questo:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::123456789012:saml-provider/MyCorporateIdP"
      },
      "Action": "sts:AssumeRoleWithSAML",
      "Condition": {
        "StringEquals": {
          "SAML:aud": "https://signin.aws.amazon.com/saml"
        }
      }
    }
  ]
}

Spiegazione Tecnica:

  • Principal: Chi può assumere il ruolo? Solo il provider SAML che abbiamo creato.
  • Action: Quale azione? sts:AssumeRoleWithSAML (specifica per la federation).
  • Condition: Controllo di sicurezza per assicurarsi che il login sia destinato alla console AWS.
